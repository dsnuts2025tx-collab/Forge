# Mastermind v2.1 — Necessity-Gated Upgrade Policy

Status: LOCKED

## Purpose
Continuously identify and incorporate necessary, evidence-backed improvements into Mastermind without uncontrolled architectural drift or indiscriminate feature accumulation.

## Upgrade rule
Any discovered capability, configuration, workflow, tool, security control, performance improvement, reliability mechanism, data boundary, model strategy, or infrastructure improvement may be evaluated for inclusion when it can materially improve the system.

It is eligible for implementation only when at least one of these is demonstrated:
- closes a real capability or reliability gap;
- materially improves security, privacy, compliance, resilience, performance, cost, or operability;
- materially improves customer outcomes or accessibility;
- removes an unnecessary foundational dependency;
- improves verification, auditability, recovery, or truthfulness;
- materially improves freshness, reasoning, orchestration, or worker coordination;
- is required by a changed external dependency, standard, platform, or regulation.

## No speculative bloat
Do not add technology merely because it is new, fashionable, impressive, or offered by a competitor. Every upgrade receives a necessity, compatibility, security, cost, operational, and maintenance assessment.

## Worker proposal model
Workers may independently discover and propose upgrades. Workers do not self-promote changes to production. Proposals require evidence, conflict checking, security/compatibility review, tests appropriate to impact, and Mastermind authorization.

## Continuous competitive intelligence
Maintain awareness of relevant competitor capabilities and emerging technical approaches. Competitive findings become candidate requirements only after independent evaluation. Parity is a floor; unnecessary copying is prohibited.

## Upgrade lifecycle
DISCOVER -> CLASSIFY -> EVIDENCE -> GAP ASSESSMENT -> SECURITY/COMPATIBILITY REVIEW -> COST/OPERABILITY REVIEW -> TEST -> INDEPENDENT VERIFY -> MASTER APPROVAL -> IMPLEMENT -> DEPLOY -> OBSERVE -> RECONCILE.

## Rollback
Every consequential upgrade must have an identifiable rollback/recovery path appropriate to its impact. Failed or harmful changes are not allowed to remain promoted merely because they were previously approved.

## Architecture protection
No new foundational primitive is permitted when an existing primitive can cleanly satisfy the requirement. A genuine architectural gap must be documented with compatibility, security, policy, and migration impact before a new foundational primitive is approved.

## Truthfulness
A proposed upgrade is not an implemented upgrade. Status must remain explicit: PROPOSED, IMPLEMENTED, TESTED, VERIFIED, DEPLOYED, or PRODUCTION.

## Final principle
Mastermind should become stronger continuously, but every permanent addition must earn its place through demonstrated necessity and evidence.
