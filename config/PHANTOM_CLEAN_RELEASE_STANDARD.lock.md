# PHANTOM CLEAN RELEASE STANDARD — LOCKED

**Scope:** Entire Phantom ecosystem: Phantom, Mastermind, Forge, Forge Engine, Verification, Footprints, Playground, Seven Dwarfs, Insight/PHIA, Phantom Volt, and future systems.

## Purpose

Produce one clean, clear, evidence-backed path from authorized intent to implementation, deployment, live operation, and continuous improvement.

## Non-negotiable authority

The user's explicit ruling is the highest system authority. Nothing in the ecosystem may override, silently supersede, weaken, or reinterpret it. Internal agents and subsystems operate within that authority. Hard external constraints must be surfaced explicitly.

## Role specialization + cooperative attribution

Every subsystem retains a specific canonical role. Roles are not silos: when a task crosses boundaries or another subsystem has a required capability, the owning subsystem must attribute/delegate the needed work to the appropriate capable subsystem through the canonical contracts rather than duplicate the capability or wait for user intervention.

No subsystem should require the user or G to manually coordinate ordinary cross-system assistance. Dependencies, handoffs, failures, and ownership must be machine-readable and actionable.

## Autonomous continuous work

Within the user's authorization and established policy envelope, the ecosystem is expected to continue useful work without requiring the user or G to babysit ordinary execution. It should:

1. discover the next actionable work;
2. prioritize by dependency, launch impact, risk, and value;
3. reuse existing capabilities first;
4. delegate/attribute work to the subsystem best equipped to perform it;
5. execute independent workstreams in parallel where safe;
6. resolve ordinary implementation blockers autonomously;
7. test and verify each change;
8. preserve evidence, state, provenance, and decisions;
9. reconcile desired state against observed state;
10. continue to the next actionable item.

Escalate only when a genuine authority boundary, hard safety/security/legal/compliance conflict, irreversible consequential action, unexplained integrity failure, conflicting authoritative requirement, or genuine foundational architectural gap requires it.

The system must not invent work merely to appear active. Autonomous work must be bounded, relevant, evidence-producing, and tied to an authorized objective or required system-health obligation.

## Factual research + anti-hallucination standard

Research must be as deep as materially useful and proportionate to the decision. Prefer primary/authoritative sources, repository evidence, direct system evidence, reproducible tests, and current verified data. Distinguish facts, observed evidence, inference, uncertainty, and proposals. Never fabricate sources, results, capabilities, deployments, tests, credentials, live state, or completion. When evidence is unavailable, record the exact uncertainty and continue every independent workstream that can proceed.

## Speed standard

Optimize for the fastest **correct and verified** path, not the fastest unverified claim. Parallelize independent work, reuse proven components, minimize redundant analysis, cache/reuse established evidence where valid, and move immediately from discovery to implementation when the gap is clear. Speed never permits skipped verification or invented evidence.

## Universal release pipeline

**USER RULING → G TRANSLATION → MASTERMIND PLAN/CONFIG → PHANTOM AUTHORIZATION → FORGE BUILD/INTEGRATION → TEST → INDEPENDENT VERIFICATION → PHANTOM PROMOTION DECISION → DEPLOY → HEALTH CHECK → LIVE SMOKE TEST → OBSERVE → RECORD → RECONCILE → IMPROVE**

## Required release record

Every release records, as applicable:

1. authorized objective and configuration;
2. exact source commit/artifact/version;
3. dependency and capability selection;
4. tests and regression results;
5. security/privacy/policy checks;
6. verification evidence;
7. deployment target and result;
8. health/readiness result;
9. live smoke/customer-path result;
10. rollback/recovery readiness;
11. observability/audit evidence;
12. known limitations and remaining blockers.

## Truth states

**PLANNED → IMPLEMENTED → TESTED → VERIFIED → DEPLOYED → LIVE/PRODUCTION-VERIFIED → OPERATIONAL → OBSERVED → EVOLVING**

A state may advance only with evidence appropriate to that state. Never call a system live because a deployment was requested or a URL exists.

## Failure behavior

If any release gate fails: identify the exact seam → reuse/repair existing capability → implement → test → verify → record → retry. Do not loop on explanations. Do not restart the architecture without a genuine architectural gap.

## Cross-system synchronization

All systems must consume the same authority, mission, release, evidence, and truth-state model. No system may maintain a contradictory launch state. Production claims must reconcile against observable runtime state.

## Production rule

A customer-facing launch is complete only when the intended customer journey is actually executable and live evidence proves it. After launch, monitoring, reconciliation, recovery, and bounded improvement continue.
